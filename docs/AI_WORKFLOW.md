# Одна задача — один чат

[Состояние проекта](PROJECT_STATUS.md) · [Задачи](TASKS.md) · [Оглавление](README.md)

Проект разрабатывается последовательно разными чатами Codex. Общая память — файлы и Git, а не обещание, что новый чат помнит старый. `AGENTS.md` задаёт правила, `backlog.json` хранит статусы, отчёт задачи — проверку результата, commit — точную версию файлов.

## Что писать в новом чате

Открыть этот проект в Codex и отправить:

```text
Выполни задачу T001 из docs/tasks/T001.md.
Сначала прочитай AGENTS.md и docs/PROJECT_STATUS.md, проверь зависимости.
Реализуй задачу, выполни её проверки, сохрани отчёт и обнови статус.
Зафиксируй результат в Git и отправь в приватный origin.
Следующую задачу не начинай. В конце дай commit и результат проверок.
```

В следующем чате заменить ID на следующую доступную задачу. Можно написать «Выполни следующую доступную задачу по AGENTS.md», если не хочется выбирать номер вручную. Открывать нужно тот же проект/checkout с актуальными файлами; отдельный несинхронизированный clone не знает о незапушенных изменениях.

## Файлы состояния

| Файл | Роль |
|---|---|
| `AGENTS.md` | Обязательные проектные инструкции для агента |
| `docs/backlog.json` | Единственный источник task statuses и dependencies |
| `docs/PROJECT_STATUS.md` | Генерируемая краткая сводка: сделано, активно, заблокировано, следующий шаг |
| `docs/tasks/Txxx.md` | Объём и критерии задачи; статус синхронизируется автоматически |
| `docs/task-reports/Txxx.json` | Фактический отчёт: изменения, проверки, критерии и ограничения |
| `docs/TRACEABILITY.md` | Состояние покрытия каждого design state |
| Git history | Версии исходников, отчётов и статусов; ID задачи в сообщении commit |

Не создавать второй несогласованный TODO-список и не держать результат только в ответе чата. `docs/VALIDATION.json` — историческая проверка документации; текущая проверка процесса выполняется `scripts/tasks.py check`.

## Команды

```sh
python3 scripts/tasks.py status
python3 scripts/tasks.py start T001
python3 scripts/tasks.py init-report T001
# Реализовать, выполнить проверки и заполнить отчёт реальными результатами.
python3 scripts/tasks.py finish T001
python3 scripts/tasks.py check
```

Если зависимость не завершена, start отказывает. Если другая задача in_progress, вторую стартовать нельзя. Для реальной остановки: `python3 scripts/tasks.py block T001 --reason 'что именно мешает'`. После устранения причины `start T001` возвращает её в работу. Для продолжающегося in_progress новый чат сначала выясняет, что прошлый уже не работает с тем же checkout; это не автоматический захват файлов.

Report template содержит `passed: false` для каждого критерия и пустой checks. Finish не принимает такой шаблон. У каждого критерия должно быть доказательство, у checks — фактическая команда или воспроизводимая ручная процедура с результатом passed. Скрипт проверяет структуру и последовательность, но не может доказать честность описанных результатов: агент обязан запускать проверки и не выдумывать вывод.

## Git и GitHub

Для одного человека достаточно последовательной работы в `main`: одна задача — один понятный законченный commit (большая задача может иметь промежуточные). Ветки и pull requests можно вводить по необходимости, они не обязательны для каждого шага. Два чата одновременно один checkout не меняют. Перед началом — git status/log и сверка с origin; при расхождении не делать destructive reset или force push.

После завершения и обновления статусов агент коммитит связанные файлы и делает обычный push. Если push не прошёл, локальный commit остаётся; следующий чат видит его и повторяет синхронизацию, не повторяет реализацию. GitHub Issues не обязательны: подробный backlog уже находится в репозитории.

Для обычного отката использовать `git revert <commit>`: новый commit отменяет изменение и сохраняет историю. Откатить совместно код и его task metadata; если от задачи уже зависят выполненные, сначала оценить последствия и статус потомков. Не применять `reset --hard` как обычную кнопку Undo. Git версионирует код, но не личную базу карточек: откат схемы выполняется через совместимую сборку и резервную копию.

## Личное приложение

Цель — рабочая `.app` на ноутбуке владельца, а не публичный релиз. T096–T100 теперь описывают локальную сборку, установку, обновление и восстановление. DMG, Developer ID и notarization — возможное будущее расширение при решении раздавать приложение. Сохранность данных, тесты и резервирование остаются обязательными для принятия соответствующих задач.

## Почему это работает в разных чатах

Codex использует проектный `AGENTS.md` как инструкции при начале работы; сводка и backlog лежат рядом с кодом. Это обеспечивает точку восстановления контекста, но не гарантирует правильность каждого решения нейросети. Готовность определяется критериями, выполненными проверками и историей, а не одной фразой «всё ок». [Официальная документация OpenAI](https://developers.openai.com/codex/guides/agents-md).

VS Code поддерживает Swift через расширение. Для нашего Xcode app target и XCUITest установить полный Xcode и выбрать его developer directory; пользоваться его IDE постоянно не нужно. Codex может вызывать сборку/тесты из терминала. [Swift в VS Code](https://docs.swift.org/latest/documentation/userdocs/), [инструменты Xcode](https://developer.apple.com/documentation/xcode/xcode-command-line-tool-reference).
