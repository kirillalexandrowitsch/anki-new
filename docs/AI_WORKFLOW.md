# Одна задача — один автономный цикл

[Состояние](PROJECT_STATUS.md) · [Задачи](TASKS.md) · [Бюджет](BUDGET.md)

Пользователь поручил Codex самостоятельно реализовывать выбранную задачу, делать commit/push, создавать PR, исправлять CI и продвигать результат task/Txxx → dev → stage → main. Ручное нажатие Push/Merge не требуется. Это разрешение относится к данному репозиторию и штатному процессу ниже; обход проверок и дополнительные платежи запрещены.

## Промпт нового чата

```text
Выполни следующую доступную задачу по AGENTS.md полностью.
Сам выбери её из актуальной origin/dev, реализуй, проверь и сохрани отчёт.
Доведи PR через dev → stage → main с зелёными проверками на каждом шаге.
Исправляй ошибки CI; проверки и критерии не ослабляй.
Следующую задачу после этой не начинай. В конце дай PR и результат проверок.
```

Можно указать Txxx явно. Один запуск выполняет одну задачу вместе с доставкой. При запросе нескольких задач агент повторяет тот же цикл последовательно. Файлы/Git являются памятью проекта; новый чат не обязан помнить старый разговор.

## Ветки

| Ветка | Назначение |
|---|---|
| task/Txxx | Временная ветка одной реализации от origin/dev |
| dev | Интеграция принятой задачи |
| stage | Проверка кандидата перед стабильной веткой |
| main | Принятая стабильная версия исходников |
| maintenance/<slug> | Изменения процесса/docs/CI/scripts с отдельным отчётом, без реализации app sources |

Постоянные ветки принимают только PR. PR в stage имеет head=dev, PR в main имеет head=stage. Прямое изменение main/dev/stage, force push, admin bypass и отключение обязательных проверок не входят в разрешённый цикл.

## Выполнение

1. Проверить git status/log. При чистом checkout выполнить `python3 scripts/start_task.py next` или явный Txxx. Скрипт fetch сверяет деревья origin/dev/stage/main, не даёт начать следующую задачу до окончания предыдущей доставки, читает backlog из origin/dev и создаёт task-ветку с готовыми dependencies. Дальше агент читает карточку и выполняет её, не останавливается после создания ветки.
2. Реализовать изменение, проверить критерии, создать `python3 scripts/tasks.py init-report Txxx`, заполнить его реальными evidence/checks. Блокеры сохранять честно; done без обязательной проверки запрещён.
3. `python3 scripts/tasks.py finish Txxx`, затем `python3 scripts/ci.py quality`. На локальном Mac также выполнить доступные app-проверки; CI на macOS не заменяет проверку пользовательских разрешений на ноутбуке владельца.
4. Закоммитить код, отчёт и статусы с ID задачи. Затем `python3 scripts/deliver.py --task Txxx`.
5. Скрипт push создаёт или находит PR в dev, ждёт quality/macos. Только SUCCESS обоих разрешает merge. После merge он ждёт зелёный push pipeline, создаёт PR dev→stage, повторяет проверки/merge, затем stage→main и снова проверяет push pipeline.
6. При ошибке читать `gh run view <run-id> --log-failed`, исправлять причину, коммитить и повторять доставку. Если исходная задача уже попала в dev, исправляющий commit остаётся на её task-ветке и обновляет её отчёт; CI принимает такой repair без ослабления критериев. Успешно merged PR повторно не создаётся на том же candidate SHA.
7. Вернуть фактические PR links, commits, результаты CI и следующую задачу. Новый цикл всегда стартует из актуальной origin/dev. После неоконченной доставки сначала закончить/исправить её, не брать следующий независимый номер.

## Что проверяет CI

Workflow `.github/workflows/ci.yml` содержит JSON — допустимое подмножество YAML, поэтому его политика проверяется без стороннего YAML-пакета.

- quality: граф и отчёты задач, generated state consistency, Python tests, локальные ссылки, хеши всех 48 PNG, маршрут PR, наличие task report и неизменность критериев принятия задачи.
- macos: те же базовые проверки на стандартном macos-15 и проверка Xcode. Когда появляется app target, обязательно выполняется xcodebuild test; новые Swift packages должны быть зарегистрированы и тестируются через swift test.
- T002 нельзя принять без app.project/app.scheme/packagePaths в `.github/automation.json`. Пока app target отсутствует, лог прямо говорит, что проверяется документация/процесс; успешная сборка приложения не заявляется.

Оба check names стабильны и обязательны в branch protection. GitHub допускает skipped/neutral в некоторых правилах, но наш deliver.py их явно отвергает. Скрипт также сверяет публичность репозитория, защиту администратора, head SHA и неизменность target branch во время ожидания. Изменение target требует свежей проверки candidate.

Защита использует strict=false только для требования ancestry/up-to-date, чтобы последовательные merge-коммиты постоянных веток не требовали циклических back-merge. Это не разрешение красного CI: проверяется PR merge result, а deliver.py повторно проверяет target SHA перед merge.

## Отчёты и статусы

Источник статусов — docs/backlog.json. Карточки/реестр/трассировка/сводка синхронизируются scripts/tasks.py sync. done означает выполнение критериев в данной версии ветки. Попадание в dev/stage/main подтверждается PR и зелёными post-merge runs. Не записывать в отчёт собственный будущий commit hash; он доступен через Git.

Report template начинается с passed=false и пустых checks. Структурная проверка не доказывает истинность текста — агент обязан реально выполнять процедуры. Цельные screenshots/логи оставлять в разрешённых локальных местах; большие CI artifacts/cache uploads не нужны.

## Бесплатность и доступ

Репозиторий публичный по подтверждённому решению владельца, включая допустимость чужих копий. Стандартные ubuntu-24.04/macOS-15 runners бесплатны для public; larger runners и metered storage не используются. Если репозиторий снова станет private, workflow jobs не запускаются, а deliver.py остановится. Нельзя автоматически покупать тариф или продолжать платные запуски.

Codex работает локально через уже имеющуюся подписку и gh login. GitHub Actions только запускают проверки; OpenAI API key и Apple Account в pipeline не нужны. CI token имеет только contents:read. Merge делает авторизованный локальный gh, без автоматического списания на AI API.

Для обычного запуска macOS .app на своём Mac вход Apple Account в Xcode не нужен при выбранной локальной подписи и отсутствии capabilities с provisioning. Загрузка Xcode через Apple может потребовать учётную запись. [Apple о запуске macOS app](https://developer.apple.com/documentation/xcode/running-your-app-on-simulated-or-physical-devices).

При реальных внешних блокерах — системном запросе, недоступном доступе, лимите Codex — сохранить прогресс и конкретную причину. Зелёный CI не гарантирует отсутствие всех ошибок приложения; его проверки расширяются вместе с реализацией.

## Публичность и откат

После открытия исходники, дизайн, документация и история доступны другим людям. Возврат в private не отзывает скачанные копии. Личная коллекция, ключи, записи микрофона и пароли в Git не входят. При кодовом откате учитывать статусы зависимых задач; пользовательская SQLite-база откатывается отдельной совместимой копией, а не git revert.
