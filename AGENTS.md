# Anki New: инструкции для каждого нового чата

Это личное нативное macOS-приложение для MacBook владельца на Apple Silicon. Публичная публикация, App Store, платная подписка Developer Program и notarization не нужны для принятия задач. Стек и контракты — в docs/. Пользователь вправе менять эти решения явным поручением.

## Начало работы

1. Прочитать `docs/PROJECT_STATUS.md`, `docs/AI_WORKFLOW.md` и карточку запрошенной задачи `docs/tasks/Txxx.md`. Источник статусов — `docs/backlog.json`, а не история чата. Проверить `git status` и последние коммиты; не трогать чужие незакоммиченные правки.
2. Выполнить `python3 scripts/tasks.py status`. Если задача уже done, показать её отчёт/коммит и не реализовывать повторно. Если dependencies не done, сообщить конкретные недостающие задачи; не помечать их выполненными ради продолжения.
3. Прочитать относящиеся к задаче архитектурные контракты и изображения по её ссылкам. Не загружать весь архив промптов и все 100 карточек без необходимости.
4. Вести одну задачу за раз в общем checkout. `python3 scripts/tasks.py start Txxx` фиксирует начало. Не забирать in_progress из другого активного чата без разрешения пользователя. Продолжение той же задачи согласовать по состоянию файлов и журналу.

## Реализация

- Делать весь объём карточки, включая проверку; не останавливаться на плане. Следующую самостоятельную задачу автоматически не начинать.
- Core не зависит от SwiftUI/GRDB; Features не выполняет SQL. Данные, scheduler, файлы и UI разделены по ARCHITECTURE.md.
- До reveal только «Показать ответ» плюс skip/audio; оценки Снова/Трудно/Хорошо/Легко только после. Editor Save явный, general settings autosave; Cancel/Escape не применяет draft.
- Проверки данных выполнять на временной коллекции, не на личной. Существующие PNG не менять и не регенерировать без запроса. Секреты, пользовательские коллекции, записи микрофона и build artifacts в Git не добавлять.
- Xcode — инструменты сборки; писать/править файлы можно из Codex или VS Code. Отсутствующие Xcode/SDK/разрешения — реальные ограничения проверки, а не повод заявить, что тесты прошли.

## Завершение и передача

1. Проверить каждый критерий карточки. Записать `docs/task-reports/Txxx.json`: сделанное, фактические команды и результаты, критерии, оставшиеся ограничения. Шаблон создаёт `python3 scripts/tasks.py init-report Txxx`; шаблон изначально НЕ подтверждает готовность.
2. Если проверка не выполнена или критерий не достигнут, не ставить done. Использовать `python3 scripts/tasks.py block Txxx --reason 'конкретная причина'`; сохранить частичный результат и безопасный commit при необходимости.
3. При выполненных критериях: `python3 scripts/tasks.py finish Txxx`, затем `python3 scripts/tasks.py check`. Команда finish проверяет полноту отчёта, но не заменяет реальные тесты.
4. Сделать содержательный Git commit с ID задачи, включив код, отчёт и обновлённые статусы; добавлять файлы осознанно. После commit `python3 scripts/tasks.py status` показывает следующий доступный шаг. Синхронизировать с существующим приватным origin обычным push; не force-push и не удалять историю.
5. В итоговом ответе указать ID, что изменилось, что реально проверено, commit hash, результат push и следующую доступную задачу. Не сообщать об успешном push без подтверждения инструмента.

`docs/TASKS.md`, `docs/TRACEABILITY.md`, `docs/PROJECT_STATUS.md` и строки статуса карточек обновляются через `python3 scripts/tasks.py sync`. При изменении объёма/названия задачи синхронно обновить backlog и текст карточки; ID не перенумеровывать. Откат Git-коммита не откатывает пользовательскую SQLite-базу: учитывать миграции и проверенную копию.
