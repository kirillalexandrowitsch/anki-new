# Anki New: инструкции для каждого чата Codex

Личное нативное macOS-приложение для MacBook владельца на Apple Silicon. Репозиторий kirillalexandrowitsch/anki-new публичный по явному решению пользователя. Публичный исходный код не означает обязательную публикацию приложения: App Store, платная Developer Program и notarization не требуются.

## Бюджет

Ноль дополнительных платежей сверх уже оплаченной подписки Codex. Правила в docs/BUDGET.md. Разрешены бесплатные системные инструменты и подходящие open-source библиотеки, а также стандартные GitHub-hosted ubuntu-24.04 и macos-15 в этом публичном репозитории. Larger runners, платные API/AI-инференс, новые подписки, trial с оплатой, Codespaces, Packages и Git LFS не использовать. Artifacts/cache uploads в CI не включать без отдельного пересмотра бюджета. При возвращении репозитория в private hosted jobs остановлены условием workflow; skipped не считается успешной доставкой. Не покупать credits при исчерпании лимитов Codex.

## Автономный цикл одной задачи

Пользователь заранее поручил Codex выполнять commit, push, создавать PR, проверять Actions, исправлять ошибки и выполнять merge по цепочке task/Txxx → dev → stage → main без повторных подтверждений каждого шага. Это относится только к этому проекту и его исходникам. Системные запросы, недоступные credentials и реальные внешние блокеры могут потребовать участия пользователя; не обходить ограничения и не сообщать о несуществующем успехе.

1. Прочитать docs/PROJECT_STATUS.md, docs/AI_WORKFLOW.md и карточку задачи. Проверить git status/log. Незакоммиченные чужие изменения не удалять. Источник статусов — docs/backlog.json в актуальной origin/dev, а не предыдущий чат и не устаревшая main.
2. Для новой задачи выполнить python3 scripts/start_task.py next (или явный Txxx). Команда fetch выбирает задачу с готовыми зависимостями и создаёт task/Txxx от origin/dev. Прочитать относящиеся к ней контракты и PNG, реализовать весь объём. Одновременно один чат меняет общий checkout.
3. При продолжении существующей task-ветки сначала проверить сохранённый progress и что другой чат больше не работает. Не повторять уже выполненную задачу и не переписывать существующую ветку.
4. Выполнить реальные проверки из карточки; сохранить docs/task-reports/Txxx.json, созданный через scripts/tasks.py init-report. Все acceptance criteria должны иметь passed=true и evidence; checks содержат фактические команды/процедуры и результаты. Не ослаблять критерии или зависимости ради завершения.
5. При готовности выполнить scripts/tasks.py finish Txxx и scripts/tasks.py check. При настоящем блокере сохранить частичный результат и block с конкретной причиной, не ставить done.
6. Осознанно добавить файлы и сделать commit с ID задачи. Затем python3 scripts/deliver.py --task Txxx. Команда сама делает push, PR в dev, ждёт strictly-green CI, merge, проверяет push pipeline и продвигает PR dev→stage→main с повторной проверкой. Если CI красный — читать gh run view --log-failed, исправлять причину на task-ветке, проверять, коммитить и повторять доставку. Не заканчивать обычный запрос после одного только push или создания PR.
7. Финально проверить реальные PR, merge и pipeline results. Если создаются PR и доступен app tool attach_artifact, прикрепить каждый PR к чату. Сообщить ID, изменения, проверки, commit/PR links и следующую доступную задачу. Следующую самостоятельную задачу автоматически не начинать, если пользователь не запросил несколько.

## Обязательные ограничения merge

- Постоянные ветки main/dev/stage не пушить напрямую. Только PR; main принимает stage, stage принимает dev, dev принимает task/Txxx и ограниченные maintenance/*.
- quality и macos должны иметь conclusion SUCCESS. Failed/cancelled/skipped/neutral и отсутствие проверки не разрешают merge. Нужны выполненные критерии и сохранённый отчёт. Не использовать --admin, не отключать branch protection, не удалять/подменять tests ради зелёного результата, не использовать force push.
- Maintenance допустим для workflow/docs/scripts и имеет docs/automation-reports/<slug>.json. Он не заменяет реализацию app-задачи. Доставка: scripts/deliver.py --maintenance <slug>.
- Проверки развивать по мере появления исходников. T002 обязательно задаёт app.project, app.scheme, packagePaths в .github/automation.json. CI не позволяет принять появившийся Xcode target или выполненную T002 без настроенной сборки/тестов.
- done означает выполненные критерии в конкретной task/dev версии. Попадание в stage/main доказывается соответствующими PR и зелёным post-merge CI, а не отдельным произвольным флагом. Если доставка прервалась — продолжить её, не начинать следующую реализацию.

## Архитектурные и пользовательские правила

Core не зависит от SwiftUI/GRDB; Features не выполняет SQL. Скрытый ответ: Показать ответ плюс skip/audio; четыре оценки только после reveal. Editor Save явный, настройки autosave, Cancel/Escape не применяет draft. Личную коллекцию, секреты и записи микрофона не коммитить. Проверки на временных данных; исходные PNG не менять без запроса.

Для локального macOS app выбираем Sign to Run Locally/ad-hoc по необходимости; вход в Apple Account внутри Xcode не является условием обычного запуска на своём Mac. Загрузка Xcode через App Store/Apple downloads может потребовать Apple Account. Capabilities с provisioning не добавлять без бесплатного обоснованного пути. Codex не запрашивает пароль Apple и не помещает Apple/GitHub credentials в CI.

Статусы, TASKS.md, TRACEABILITY.md и PROJECT_STATUS.md синхронизируются scripts/tasks.py sync. Номера задач стабильны. Откат кода не откатывает SQLite-схему: учитывать миграции и резервную копию. Пользовательские явные указания имеют приоритет над этим процессом.
